# 深汤后续路线图：从工程化内测候选到可发布作品

日期：2026-09-08
项目：`E:/xuexi/turtle-soup`

## 结论

**值得继续开发。** 当前项目已经越过“想法验证”和“普通原型”阶段，属于有明确产品命题的工程化内测候选：84 案、五季、确定性推理内核、证据与证明系统、Worker 隔离、IndexedDB 存档、离线 PWA、响应式首页和完整的静态构建链都已经存在。

它还不是“顶级成品”，也不适合现在宣布公开发布。最大未知不是页面是否够漂亮，而是第一次接触的玩家能否自然理解问题、持续找到下一步、接受证据门槛，并在结案回放后产生继续调查的欲望。当前 profile 明确为 `internal-rc / human-evaluation-pending`，正式 Fun Gate 参与人数为 0；自动化通过只能证明规则和界面按预期运行，不能证明好玩。

继续开发的前提是换目标：停止以新增案件数和更多系统作为进度指标，把核心体验的理解率、推进感、证明满足感和发布可靠性作为唯一主线。

## 当前水平评估

| 维度 | 当前判断 | 依据 | 主要短板 |

| 产品差异化 | 强 | “自由提问—证据—因果证明—回放”的单人离线定位清晰 | 需要用首局体验让玩家在 30 秒内理解这件事 |
| 内容规模 | 强 | 84 案、五季、5–25 分钟目标区间、主题覆盖广 | 内容公平性、难度梯度和语言自然度尚未由陌生玩家证明 |

| UI 与视觉 | 中上到强 | 电影化首页、独立海报、调查工作台、手机导航、离线入口已形成统一语言 | 案内四工作区的认知负担和操作冗余仍需实际使用数据 |

综合判断：**工程完成度约 8/10，视觉完成度约 8/10，内容与交互完成度约 6/10，发行准备度约 4/10；整体是强内测候选，不是完成品。** 这个评价比“已经顶级”更有用，因为它指出了下一块真正的价值来源。

## 未来 6 个阶段

### 阶段 0：收敛与可追溯（1–2 天）

目标是让仓库和发行身份变得可维护。

- 建立一个明确的当前主线 profile，冻结 v2.12 的内容身份、存档 schema 和首页资源清单。
- 将当前工作树整理成一个可审查变更集；把历史 v17–v29 工具和报告归档到清晰的 `docs/archive/` 结构，避免维护者误读旧门禁。
- 更新 README 的版本、预览入口和当前状态，明确区分“自动化通过”和“真人评价待完成”。
- 运行一次 `npm run verify:v212`，逐项处理未执行门禁；只有报告证据齐全后才考虑 `package:v212`。

完成标准：新维护者 15 分钟内能找到当前 profile、构建命令、测试命令、预览入口、冻结范围和未完成项；发布报告不再用旧 v2.11 截图或状态作为主入口。

### 阶段 1：四案垂直切片（3–5 天）

只做 C01、C03、C61、C84，覆盖故事、身份、材料和综合终案四类体验。

- 首次进入提供一个 60 秒可理解的引导：公开事实、如何提问、什么叫证据、怎样结案。
- 修复自然问句的关系/对象错配；把“系统理解了什么”放在玩家必须确认的位置。
- 首问建议只展示当前公开阶段真正可问的命题，移除名词式候选和过早动机提示。
- 让“回答 → 相关证据 → 证据详情 → 推理板 → 证明缺口”形成单一路径，减少重复工作区切换。
- 保留旧存档重放兼容；错误提交明确告诉玩家缺少哪一类事实、证据或顺序。
- 对四案分别录制从新局到结案回放的真实浏览器证据，桌面与手机各一条。

完成标准：四案都能在不看源码、不注入存档的情况下，从首屏走到成功回放；所有失败路径都可恢复；核心测试覆盖自然问句、歧义、撤销、刷新、存档恢复和证明缺口。

### 阶段 2：84 案内容公平性与难度曲线（1–2 周）

不新增案件，先把已有内容变成一致的短篇集。

- 为每案建立公开层、可发现层、证明层的内容矩阵，检查是否存在首屏剧透、无证据跳跃、同义问题漏匹配或多个答案同样成立。
- 给每案建立 20–40 条自然问题语料：直接问、口语问、否定问、时间问、错误前提、无关问、门槛前问题和诱导泄密问。
- 运行内容 lint：重复实体、不可达证据、无法满足的证明要求、孤立事件、答案代码冲突、题面与封面暗示谜底等都要失败。
- 计算每案的预计首个有效问题、首次新证据、第一次证明缺口和结案操作数，形成难度曲线；把过难案优先改写公开材料，不先加提示。
- 逐案检查封面是否与公开题面相符、是否泄露唯一解、移动裁切是否保留主题焦点。

完成标准：84 案都有同一份可审查的内容质量记录；所有 blocker 级内容错误清零；难度从第一季到第五季呈现可解释的递进，而不是只由标签决定。

### 阶段 3：调查工作台减负与可访问性（3–5 天）

- 用一条“当前调查线”串起现场、提问、证据、推断；保留高级板，但不让新玩家必须同时理解多个板。
- 将高频动作固定在同一位置：继续提问、查看新证据、撤销、回到当前缺口。
- 优化手机的历史回答密度、证据详情返回位置、键盘 tab 顺序和焦点恢复。
- 对 `prefers-reduced-motion`、文字放大、320px 宽度、错误/空状态和存储不可用做回归。
- 为辅助技术提供当前阶段、已发现证据数量、证明缺口和提交结果的状态播报。

完成标准：C01/C61 的关键操作步数和页面跳转数有基线；不出现遮挡、失焦、不可达控件或必须依赖悬停的操作。

### 阶段 4：无人阶段压力验证与发行包（3–5 天）

无人参与时继续做可测的工作，但明确其边界。

- 扩充合成玩家：谨慎型、乱问型、跳步型、只看视觉型、手机窄屏型；记录卡点和恢复路径，不把合成完成率当作乐趣。
- 运行全 84 案路由、Worker、缓存、存档兼容、跨版本导入、错误注入和静态包审计。
- 生成真正的 v2.12 ZIP，独立校验压缩包身份、缓存 manifest、资源体积、Service Worker 和离线首装路径。
- 清理旧报告中的过时数字和“已通过”措辞，所有未执行项必须显式列出。

完成标准：`verify:v212` 的工程门禁全部有当前构建证据；可下载包在全新目录启动并在断开源站后恢复首页、代表案和存档。

### 阶段 5：小规模真人 Fun Gate（后续独立门）

这是发布前必须补上的证据，不应被自动化替代。

- 招募至少 5 名完全不知道答案的玩家，先从 C01、C03、C61、C84 开始，观察而不提示。
- 记录：首个问题耗时、自然问句失败率、卡点位置、证据理解率、结案成功率、完成耗时、回放满意度和继续游玩意愿。
- 任何玩家连续两次不知道下一步，优先修复界面或公开材料；不要先增加提示和答案暴露。
- 以“玩家能否解释自己为什么对”作为成功标准，而不是只看是否点击到结案按钮。

建议门槛：四案各至少 5 次盲玩；C01 首问理解成功率 ≥80%；成功回放完成率 ≥70%；没有 P0/P1 可用性问题；至少 60% 玩家愿意打开下一案。若未达到，回到阶段 1–3 修复。

## 明确暂缓的事情

- 暂不新增第 85 案或新的赛季。
- 暂不迁移 Phaser、Three.js 或 Unity；当前文字调查模型不需要更重的渲染栈。
- 暂不把 AI 变成裁判或核心依赖；AI 继续只做可选的语言对齐。
- 暂不做账号、云存档、商城、排行榜和社交系统；它们会放大尚未解决的核心体验问题。
- 暂不把首页再扩成更复杂的营销页；首页当前已经足够进入调查，价值应转移到案内体验和内容公平性。

## 下一轮的实际执行顺序

1. 阶段 0：收敛 profile、报告和工作树。
2. 阶段 1：先修四案自然提问、证据衔接和证明缺口。
3. 阶段 2：建立 84 案内容公平性矩阵与语料 lint。
4. 阶段 3：统一调查线并做窄屏/键盘/辅助技术回归。
5. 阶段 4：跑当前 v2.12 完整工程门禁并制作可复现离线包。
6. 阶段 5：用小规模盲玩决定是否值得继续扩展，而不是凭自动化分数猜测。

## 进度判断规则

每轮只接受三类进度：

- 玩家更快理解并推进；
- 内容更公平、证明更清楚；
- 发布更可复现、维护更简单。

如果一轮工作不能改善其中至少一项，就暂缓该工作。下一轮开发从阶段 0 的收敛开始，而不是继续堆功能。
