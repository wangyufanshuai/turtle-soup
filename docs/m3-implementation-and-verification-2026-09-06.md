主代理独立执行，未启动子代理，未创建其他任务或自动化，未部署、发布或推送。恢复点为 `E:/xuexi/turtle-soup-snapshots/m3-start-2026-09-06`，3,235 文件逐一 SHA 校验。未改冻结真相来使测试通过。

## 当前可审查结果

- 推理板和事件链共享同一公开事件的身份。放入板会加入当前草稿的事件集合；时间排列、因果、校准等关系仍由玩家分别组织。
- 主、备假设各自保存板、事件链、解释、证据和笔记。证明各步骤都能切换假设和撤销。
- 一组编辑原子提交，失败保留编辑前状态；删除事件清理所有板上的依赖，撤销恢复整次编辑及关系，并保留随后写的笔记。
- 错误公开事件可以放入板后提交验证。错误反馈保留原稿，指出可去检查的解释、板、事件链或证明材料。改稿后旧反馈标为需要重新检验。
- 关系可以就地更换、取消和撤销。M3 驱动条件改为有明确选中状态的按钮，也可以清空。
- 编辑已经结案的证明会重新要求检验；上一份通过的解释、回放和结案记录另行保留，不能用旧结案状态冒充当前结构成立。

## 行为边界和保存语义

`packages/mystery-core/src/proof-workspace-m3.ts` 集中处理新编辑边界；Worker 将本轮实时操作包装成显式 `revision: m3` 命令。`proof_action` 封装一个兼容操作；`edit_proof` 封装同一草稿至多 32 个证明操作；`undo_proof_edit` 撤销当前草稿最近一次组合编辑，保留至多 30 次记录。

旧命令仍按旧 reducer 语义重放。M3 profile 首次编辑旧共享板时复制成两份草稿，之后独立更新。canonical 身份、84 案真相、schema-one 外壳没有改写。旧客户端不能理解新命令时会拒绝该档，原档不变；这不是声称新档可在旧客户端使用。没有把新的交互语义塞进旧命令回放。

板上同一事件的引用可以共享；槽位位置和时间顺序不等价，也不自动产生因果连接。只从板上移除引用，不删事件链；从事件链删事件，则清理当前草稿各板对该事件的引用和入出边。组合移动结束后再清理依赖，所以交换两个保留节点不会无故丢失关系。

撤销问题只撤回那次回答的作用，保留后来检查的材料。如果该回答仍是某个草稿事件的唯一公开依据，整次撤销被拒绝并说明应先从事件链撤下片段，原稿、问题和材料保持。这是显式依赖保护，不是静默丢弃草稿。

当前结构改变后需要重新提交；撤销恢复结构也不会自动恢复“已结案”。当前不成立的结构不能请求一份新的已验证回放。已核实材料和另一份草稿仍引用的证据不会因当前稿移除链接而被错误降级。

严格时间循环只检查 `precedes` 与 `sampled-before`，不会把触发、重叠、缓冲或来源关系转换为时间先后。最后专门审查多时间板边界：84 案中只有 C33 同时有两张允许严格先后的板；其两套完整证书按相同顺序覆盖各自四节点。枚举全部 24 种追加连接，12 种倒序均不能结案，12 种顺序连接保持成立。未复现新的错误结案。当前反馈按单板定位；未来加入部分排序或新的多时间板内容时，需要另加跨板合并图验证和版本策略，不能从这个冻结库结果推断任意新图都已覆盖。

## 无人测试条件下，仍需要解决的内容问题

C61 的许多材料只是说某名词“在该阶段可复核”。缺少量值、单位、芯径/厚度等测量前提、基准和误差条件。当前校准与物料板可以操作通过，但材料不足以独立支持具体槽位和关系选择。两条“胶带圈数的材料能否复核？”与“停止命令的材料能否复核？”仍未被语言层直接正确覆盖，留出检查诚实保留这两个缺口。

C84 的材料同样存在名词式记录，接收命令、完成交接和审计写入的关系缺少可核对的具体记录。冻结事件的阶段标签、时间和要求连接并不自然构成玩家可解释的完整过程。反事实板提示组织错误假设，但当前事件库没有独立的反事实条件对象。其正确提交和回放说明实现路径可走通，不构成内容公平性或因果充分性的证明。

这些属于 TS-015 的内容版本工作，不能通过表现层伪造测量值、消息时刻、因果或替代路径来修补。正式 Fun Gate 人数仍为 0。C01/C03 本轮没有完整通关；其他家族实际 UI、Firefox/WebKit、全面键盘与屏幕阅读器、M3 离线/归档完整矩阵未执行。原 v2.12 的 28 项旧门禁仍保留原状态，不被这次 8 条样板流程改成通过。

## 接下来可连续执行的三个开发包

### A：TS-015 两案内容版本提案与可读材料原型

先为 C61/C84 各建立逐命题对照：玩家需要证明什么、哪份公开材料支持、现有缺口、可允许的错误推断、揭示时机、最终回放出处。独立修订版本标识与 canonical/hash 方案，保留旧案和旧档可重放。该包先产提案和原型，不直接覆盖冻结 JSON。

C61 必须补齐测量对象与基准、输入/输出单位、观测条件、允许误差、候选解释可区分的观测、圈数与长度的实际关系。具体数值从经核对的案件修订设计产生，不能用 UI 假造。验收需要至少一个能排除“被剪走一段”的公开观察和一条材料→关系→结论的可追溯证明。

C84 必须把命令标识、接收、允许继续的工作状态、交接完成、审计写入分别定义，说明记录来源、时基和可以比较的顺序；给出能排除其他路径的实际条件。反事实要有明确“如果改变什么，会观察到什么”的对象及证据，不能靠事件名占槽。验收逐个检查时间顺序、因果、反事实是否各自有依据。

完成条件：两案材料能独立阅读；每条必需事实都有公开出处；没有未定义术语或名词占位；旧版本身份未变；新版本不能默默接收旧已解结果。代理可做带出处的理解检查，但报告仍称合成检查。

### B：TS-013/014 扩展交互家族与输入等价

在内容提案明确后补充身份/来源、空间、状态、队列的代表案。先从现有内容审查中选一个材料充分的案例，再实现家族特有操作；不先把所有板统一成相同拖放壳。

为每家族定义状态不变量、三条错误但合法的探索路径、原子失败和撤销路径。每个关键操作提供点击和键盘路径，实际验证焦点、选择状态、撤销后焦点和手机滚动。时间与测量沿用本轮共享引用，但不把校准、流量、时间和因果合并成一种判定。新增多时间板/部分排序前补上跨板矛盾用例及版本化规则。

完成条件：六家族各有一个代表案的实际错误→修正→提交→回放、两视口及键盘覆盖；明确最终构建身份。当前两案成功记录不抵扣其他四类。

### C：TS-018/019 恢复与完整交付验证

依次做保存失败、双标签冲突、旧档升级、新旧版本拒绝、归档往返和离线恢复。每项先制造故障，再验证原件保留和恢复后的玩家可见状态。之后再扩充 C01/C03 完整解答路径、三浏览器引擎矩阵、音频/减少动态/对比/焦点，以及独立制品验证。

完成条件：故障可复现、不会默默丢档或放行无效结果，最终 UI 和产物均绑定同一源码/构建；未执行项继续保留。外部发布不在本轮授权动作内。

上述顺序把内容可推理性放到下一轮优先级最高处。完整 84 案修订仍逐批进行，不能用平均通过率覆盖材料不足的个案。
