# 最终产品形态与无人打磨路线（阶段提纲，待确认）

用途：面向项目拥有者的产品解释与实施决策提纲。不是已经完成的产品说明，不是上线或外部部署授权。详细逐文件实施规格在此结构确认后展开。

## 1. 项目定位

当前：有价值的确定性推理底座、84案内容库、基本统一的离线调查壳；但不是已达到精品水平的84案合集。恢复/开场曝光/门禁口径有实证缺陷，后期公共语义与操作差异尚欠打磨。

最终目标：**中文、单人、离线优先的可证明推理短篇集**。玩家靠观察和问题建立自己的解释，再用清晰的证据操作检验它。系统应让人感觉在调查一件事，而不是填写逻辑数据库。

84案是现有内容库边界，不是质量成绩。先把代表案做成可以复用的体验样板，再逐案认证，不增加C85。

## 2. 玩家最终看到的产品

| 表面 | 应完成的玩家任务 | 需要避免 |
|---|---|---|
| 案件书架 | 继续上次调查、挑一个故事、快速了解题材和目标时长 | 一屏全部技能术语、开发版本名占据首要位置 |
| 现场 | 看清异常、检查具体物件/记录，形成第一个疑问 | 主图只是一张装饰卡；唯一线索依赖颜色或声音 |
| 提问 | 一次一个命题；回答先出现，理解歧义时再确认 | 回答前弹出多个重复候选/教程/建议；未识别被当作失败 |
| 证据 | 读来源、观察、已知边界；直接支持或反驳自己的解释 | 把最终解释当“观察”，堆模板证据，名词是否成立 |
| 推断 | 自由总结→选择已知事件→建立必要关系→提交 | 开场预选完整正确答案；重复在板和时间链填同一信息 |
| 结案 | 自己的解释与逐步证据回放对照，理解为何成立 | 模板赞美、只给对错、无限高分刺激 |
| 重玩 | 限問、最小证据、无辅助三种明确约束，技能档案本地保存 | 以日期/连胜/强制解锁诱导回访；对已知真相声称无限解谜价值 |

主界面仍保留现场/提问/证据/推断四工作区，桌面轻量调查本、手机单栏；但同一状态只保留一个主动作。结果/证据为视觉主角。黑色档案室、暖纸白、少量案件强调色保留，功能文字恢复到正常阅读尺寸。

提问主反馈设计目标：短事实回答→系统理解的句子→可追溯材料入口；仅在确有歧义时显示一个最多3项的确认组。AI可选、默认关闭，不负责真相。新手首问示例必须随案件变化。

## 4. 建议的板交互家族

这是假设方案，需要B阶段样板验证，不预先宣称更好玩。

| 家族 | 真正不同的操作 | 覆盖方向 |
|---|---|---|
| 时间/区间 | 排列事件、对齐参考时间、标记区间重叠 | timeline、interval、sampling-window、时间型reference-frame |
| 身份/来源 | 人物—外观—凭证关系格、连保管/授权链 | identity-matrix、provenance-chain |
| 空间/路径 | 放置观察者/物件、选经过路径、标遮挡 | spatial-map、occlusion、acoustic、network、空间型reference-frame |
| 状态/因果 | 设置前后状态并关联触发、保持、反馈 | state-trace、causal、control、signal |
| 测量/守恒/阈值 | 区分观测和基准、归类分量、验证已有约束 | calibration、measurement、balance、aggregate、uncertainty、threshold |
| 队列/替代解释 | 组织进入/处理/确认过程或假设—排除树 | queue、capacity、counterfactual |

若冻结数据只有事件槽和关系，UI只能提供这些真实能力；没有数值模型时不能假装可计算任意曲线。更强物理推理需要新的版本化内容/证明规则，并保留原案。

## 5. 内核的终态

- 内容包：冻结事实/事件/证书/身份；公开呈现和语言别名分别版本化。
- 游戏 reducer：纯确定性状态转移。即时路径、确认路径、重放路径使用同一过渡定义。
- 接受/待确认/拒绝/已提交的语义明确；“尚未计费”不能被误解为“不需持久化上下文”。
- Worker适配层：会话生命周期、请求序列、错误码与公开投影；不会把内部异常原文当玩家反馈。
- 存档层：旧schema-one可读、历史命令夹具独立、迁移显式、原档保留；不完整日志不假装修复。
- 推理义务：判定结果附缺口类别和已公开证据依据，不通过反馈公布下一步答案；成功仍要求事实和证据充分。
- 语言桥：规则优先、无歧义才回答；AI只排序允许候选、必须确认、超时可手动继续。
- 资源/界面状态/AI缓存/诊断各自隔离，不进入真相判定。

特别说明：本地离线游戏所有内容最终都能被有意查看源码的人获取。Worker是防意外曝光、隔离UI和控制信息流的边界，不是防破解的保密服务器。验收应检查正常玩法看不到未公开信息，而不是作不可能的客户端绝密承诺。

## 6. 无人条件下的验收策略

三类证据必须分开：

1. 可证明性质：错误理论不胜、必要证据变异、命令合法性、跨案拒绝、即时与重放等价。
2. 可自动观测：操作是否达成、焦点、溢出、真实下载、长任务、键盘/触摸、刷新与离线恢复。
3. 启发式评审：故事是否抽象、视觉是否一致、推理是否有意外感。可由多个模型互审并给反例，不能称真人或完全独立。

避免自证循环：答案驱动fixture保留为底层oracle；无答案公开投影玩家另建；真实UI通关不许访问内部state/注入已解存档；开发语料与最终验收语料分离；测试报告来源与修改必须可追溯。持有正确路线的E2E只能证明操作可行，仍不等于盲推理。

拟议量化目标（不是当前实测值）：

- 84/84冻结身份与历史夹具；所有必要证据/所有作者错误理论逐个测试；自然歧义确认后的每个保存点等价。
- 全局横向溢出0（有意设计的局部横向浏览需明确可发现）；正文目标16–18px，操作标签目标至少14px；主要触控区域44px；200%缩放可用。
- lab明确设备/CPU/网络条件下，常规操作从输入到可见反馈p95≤100ms、交互阻塞≤200ms；不伪造field INP。冷启动LCP目标≤2.5s、CLS≤0.1，视基准平台验证。
- 首页静态JS先不超过现有700KB口径，再以可测收益争取≤500KB；网络按“前台启动/后台缓存/用户完整下载”分别预算。
- serious/critical axe=0之外，再做非视觉键盘与焦点验证；缺引擎依赖标not-run，不能返回空数组pass。
- 静态包/单文件/媒体包分别记录；若确需突破旧预算，先记录收益和新预算决定，不悄悄放宽。
